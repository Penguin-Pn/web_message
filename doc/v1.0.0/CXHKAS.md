# <a id="english"></a>🇺🇸 CXHKAS Protocol Specification
**Penguin Web Messaging - E2EE Service**

## 1. Introduction
Penguin Web Messaging operates on a dual-service architecture:
1. **Normal Chat:** High-speed, synchronized, and feature-rich messaging.
2. **E2EE Service:** Maximum security and privacy using the **CXHKAS** protocol family.

The **CXHKAS** (Comparison of X Hashes, Key Asymmetric, Symmetric) protocol is designed to eliminate Man-in-the-Middle (MitM) attacks by utilizing a Live Video Call as an Out-of-Band (OOB) verification channel. The server is treated as untrusted (Trustless Architecture), and identity verification is performed entirely by the users.

This document defines two variants of the protocol:
- **C2HKAS:** For 1-on-1 secure chats (2 Hashes).
- **C3HKAS:** For Group secure chats (3 Hashes).

## 2. C2HKAS (1-on-1 Chat)
**C2HKAS** stands for **C**omparison of **2** **H**ashes, **K**ey **A**symmetric, **S**ymmetric.

### 2.1. Handshake Flow
1. **Asymmetric Key Generation:** User 1 generates an Asymmetric Key Pair (Public/Private). User 2 does not need a persistent asymmetric key pair.
2. **Public Key Exchange:** User 1 sends their Public Key to User 2 through the server.
3. **Hash Comparison 1 (Root):** User 1 and User 2 initiate a Live Video Call. They compare the cryptographic hash of User 1's Public Key (e.g., an 8-character fingerprint: `B J H 7 - G 5 A R`).
4. **Symmetric Key Generation:** Once verified, User 2 generates a strong Symmetric Key (e.g., AES-256-GCM). User 2 encrypts it using User 1's verified Public Key and sends it via the server.
5. **Decryption & Hash Comparison 2 (Payload):** User 1 decrypts the Symmetric Key using their Private Key. Both users compare the hash of the Symmetric Key during the live video call.
6. **Session Established:** If both hashes match, the E2EE session is established. All subsequent messages use this Symmetric Key.

## 3. C3HKAS (Group Chat)
**C3HKAS** stands for **C**omparison of **3** **H**ashes, **K**ey **A**symmetric, **S**ymmetric.

In large groups, it is impractical for the Admin to verify keys with every member individually. C3HKAS solves this using a **Chain of Trust**.

### 3.1. Handshake Flow
1. **Admin Root Verification:** The Admin and User 1 perform C2HKAS. User 1 verifies the Admin's Public Key hash.
2. **Chain Distribution:** User 1 verifies User 2's Public Key and sends the encrypted Symmetric Key to User 2. User 2 verifies User 3, and so on.
3. **Offline Support:** If a user is offline, the chain pauses for them. The previous user holds the key until the offline user returns.
4. **Hash Comparison 3 (Group Payload):** The Admin broadcasts the final Group Symmetric Key hash. All online users compare this hash.
5. **Malicious Actor Isolation:** If a user's hash does not match the Admin's hash, the chain is audited backward. The node where the key was tampered with is identified as the Malicious Actor.

## 4. Security Considerations
- **Trustless Server:** The server only acts as a relay and cannot read the Symmetric Keys.
- **Out-of-Band (OOB) Verification:** The Live Video Call is the ultimate source of truth against MitM attacks.
- **Forward Secrecy:** (Future Scope) Keys can be rotated using the Double Ratchet algorithm for enhanced security.

# <a id="persian"></a>🇮🇷 مشخصات پروتکل CXHKAS
**پیام‌رسان وب پنگوئن - سرویس E2EE**

## ۱. مقدمه
پیام‌رسان پنگوئن بر پایه یک معماری دو سرویسی کار می‌کند:
۱. **چت عادی (Normal Chat):** پیام‌رسانی پرسرعت، همگام‌سازی شده و با امکانات کامل.
۲. **سرویس E2EE:** امنیت و حریم خصوصی حداکثری با استفاده از خانواده پروتکل‌های **CXHKAS**.

پروتکل **CXHKAS** (مقایسه X هش، کلید نامتقارن، متقارن) برای حذف حملات مرد میانی (MitM) با استفاده از یک تماس ویدیویی زنده به عنوان یک کانال تایید خارج از باند (OOB) طراحی شده است. سرور به عنوان یک محیط غیرقابل اعتماد (معماری بدون اعتماد) در نظر گرفته می‌شود و تایید هویت کاملاً توسط کاربران انجام می‌شود.

این سند دو نوع از این پروتکل را تعریف می‌کند:
- **C2HKAS:** برای چت‌های امن یک‌به‌یک (۲ هش).
- **C3HKAS:** برای چت‌های امن گروهی (۳ هش).

## ۲. پروتکل C2HKAS (چت یک‌به‌یک)
**C2HKAS** مخفف **مقایسه ۲ هش، کلید نامتقارن، متقارن** است.

### ۲.۱. فرآیند دست‌دادن (Handshake)
۱. **تولید کلید نامتقارن:** کاربر ۱ یک جفت کلید نامتقارن (عمومی/خصوصی) تولید می‌کند. کاربر ۲ نیازی به داشتن جفت کلید نامتقارن دائمی ندارد.
۲. **تبادل کلید عمومی:** کاربر ۱ کلید عمومی خود را از طریق سرور برای کاربر ۲ می‌فرستد.
۳. **مقایسه هش ۱ (ریشه):** کاربر ۱ و ۲ یک تماس ویدیویی زنده برقرار می‌کنند و هش رمزنگاری‌شده کلید عمومی کاربر ۱ را با هم مقایسه می‌کنند (مثلاً یک اثر انگشت ۸ کاراکتری).
۴. **تولید کلید متقارن:** پس از تایید، کاربر ۲ یک کلید متقارن قوی (مثل AES-256-GCM) تولید می‌کند. کاربر ۲ این کلید را با کلید عمومی تاییدشده کاربر ۱ رمز می‌کند و از طریق سرور می‌فرستد.
۵. **رمزگشایی و مقایسه هش ۲ (محتوا):** کاربر ۱ کلید متقارن را با کلید خصوصی خود باز می‌کند. هر دو کاربر هش کلید متقارن را در همان تماس ویدیویی مقایسه می‌کنند.
۶. **برقراری نشست:** در صورت تطابق هر دو هش، نشست E2EE برقرار می‌شود. تمام پیام‌های بعدی با این کلید متقارن رمزنگاری می‌شوند.

## ۳. پروتکل C3HKAS (چت گروهی)
**C3HKAS** مخفف **مقایسه ۳ هش، کلید نامتقارن، متقارن** است.

در گروه‌های بزرگ، تایید تک‌به‌تک کلیدها توسط ادمین غیرعملی است. C3HKAS این مشکل را با استفاده از **زنجیره اعتماد** حل می‌کند.

### ۳.۱. فرآیند دست‌دادن (Handshake)
۱. **تایید ریشه ادمین:** ادمین و کاربر ۱ پروتکل C2HKAS را انجام می‌دهند. کاربر ۱ هش کلید عمومی ادمین را تایید می‌کند.
۲. **توزیع زنجیره‌ای:** کاربر ۱ کلید عمومی کاربر ۲ را تایید می‌کند و کلید متقارن رمزنگاری‌شده را به او می‌فرستد. کاربر ۲ این کار را برای کاربر ۳ انجام می‌دهد و الی آخر.
۳. **پشتیبانی آفلاین:** اگر کاربری آفلاین باشد، زنجیره برای او متوقف می‌شود. کاربر قبلی کلید را نگه می‌دارد تا کاربر آفلاین برگردد.
۴. **مقایسه هش ۳ (محتوای گروه):** ادمین هش کلید متقارن نهایی گروه را اعلام می‌کند. تمام کاربران آنلاین این هش را مقایسه می‌کنند.
۵. **ایزوله کردن عامل مخرب:** اگر هش کاربری با هش ادمین نخواند، زنجیره به عقب بررسی می‌شود. گرهی که در آن کلید دستکاری شده است به عنوان عامل مخرب شناسایی می‌شود.

## ۴. ملاحظات امنیتی
- **سرور بدون اعتماد:** سرور فقط نقش رله (ارسال‌کننده) را دارد و نمی‌تواند کلیدهای متقارن را بخواند.
- **تایید خارج از باند (OOB):** تماس ویدیویی زنده، منبع نهایی حقیقت در برابر حملات MitM است.
- **رازداری رو به جلو (Forward Secrecy):** (برای آینده) کلیدها می‌توانند با الگوریتم Double Ratchet برای امنیت بیشتر چرخش پیدا کنند.

# <a id="arabic"></a>🇸🇦 مواصفات بروتوكول CXHKAS
**مراسلة الويب Penguin - خدمة E2EE**

## 1. مقدمة
يعمل Penguin Web Messaging على بنية ذات خدمتين:
1. **الدردشة العادية (Normal Chat):** مراسلة عالية السرعة ومتزامنة وغنية بالميزات.
2. **خدمة E2EE:** أقصى درجات الأمان والخصوصية باستخدام عائلة بروتوكول **CXHKAS**.

تم تصميم بروتوكول **CXHKAS** (مقارنة X من التجزئات، مفتاح غير متماثل، متماثل) للقضاء على هجمات الوسيط (MitM) باستخدام مكالمة فيديو مباشرة كقناة تحقق خارج النطاق (OOB). يتم التعامل مع الخادم على أنه غير موثوق (بنية Trustless)، ويتم التحقق من الهوية بالكامل بواسطة المستخدمين.

يحدد هذا المستند نسختين من البروتوكول:
- **C2HKAS:** للدردشات الآمنة الفردية (تجزئتان).
- **C3HKAS:** للدردشات الآمنة الجماعية (3 تجزئات).

## 2. C2HKAS (دردشة فردية)
**C2HKAS** تعني **م**قارنة **2** **ت**جزئة، **م**فتاح **غ**ير متماثل، **م**تماثل.

### 2.1. تدفق المصافحة
1. **توليد مفتاح غير متماثل:** يقوم المستخدم 1 بإنشاء زوج مفاتيح غير متماثل (عام/خاص). لا يحتاج المستخدم 2 إلى زوج مفاتيح غير متماثل دائم.
2. **تبادل المفتاح العام:** يرسل المستخدم 1 مفتاحه العام إلى المستخدم 2 عبر الخادم.
3. **مقارنة التجزئة 1 (الجذر):** يبدأ المستخدم 1 والمستخدم 2 مكالمة فيديو مباشرة. يقارنان التجزئة المشفرة للمفتاح العام للمستخدم 1 (مثل بصمة مكونة من 8 أحرف: `B J H 7 - G 5 A R`).
4. **توليد مفتاح متماثل:** بمجرد التحقق، يقوم المستخدم 2 بإنشاء مفتاح متماثل قوي (مثل AES-256-GCM). يقوم المستخدم 2 بتشفيره باستخدام المفتاح العام الذي تم التحقق منه للمستخدم 1 ويرسله عبر الخادم.
5. **فك التشفير ومقارنة التجزئة 2 (الحمولة):** يقوم المستخدم 1 بفك تشفير المفتاح المتماثل باستخدام مفتاحه الخاص. يقارن كلا المستخدمين تجزئة المفتاح المتماثل خلال مكالمة الفيديو المباشرة.
6. **تأسيس الجلسة:** إذا تطابقت كلتا التجزئتين، يتم تأسيس جلسة E2EE. تستخدم جميع الرسائل اللاحقة هذا المفتاح المتماثل.

## 3. C3HKAS (دردشة جماعية)
**C3HKAS** تعني **م**قارنة **3** **ت**جزئات، **م**فتاح **غ**ير متماثل، **م**تماثل.

في المجموعات الكبيرة، من غير العملي للمسؤول التحقق من المفاتيح مع كل عضو بشكل فردي. يحل C3HKAS هذه المشكلة باستخدام **سلسلة الثقة**.

### 3.1. تدفق المصافحة
1. **التحقق من جذر المسؤول:** يقوم المسؤول والمستخدم 1 بإجراء C2HKAS. يتحقق المستخدم 1 من تجزئة المفتاح العام للمسؤول.
2. **توزيع السلسلة:** يتحقق المستخدم 1 من المفتاح العام للمستخدم 2 ويرسل المفتاح المتماثل المشفر إلى المستخدم 2. يتحقق المستخدم 2 من المستخدم 3، وهكذا.
3. **دعم عدم الاتصال:** إذا كان المستخدم غير متصل بالإنترنت، تتوقف السلسلة بالنسبة له. يحتفظ المستخدم السابق بالمفتاح حتى يعود المستخدم غير المتصل.
4. **مقارنة التجزئة 3 (حمولة المجموعة):** يبث المسؤول تجزئة المفتاح المتماثل النهائي للمجموعة. يقارن جميع المستخدمين المتصلين هذه التجزئة.
5. **عزل الفاعل الخبيث:** إذا لم تتطابق تجزئة مستخدم مع تجزئة المسؤول، يتم تدقيق السلسلة بشكل عكسي. يتم تحديد العقدة التي تم التلاعب بالمفتاح فيها على أنها الفاعل الخبيث.

## 4. اعتبارات أمنية
- **خادم غير موثوق:** يعمل الخادم فقط كمرحل ولا يمكنه قراءة المفاتيح المتماثلة.
- **التحقق خارج النطاق (OOB):** مكالمة الفيديو المباشرة هي المصدر النهائي للحقيقة ضد هجمات MitM.
- **السرية الأمامية (Forward Secrecy):** (نطاق مستقبلي) يمكن تدوير المفاتيح باستخدام خوارزمية Double Ratchet لتعزيز الأمان.

# <a id="korean"></a>🇰🇷 CXHKAS 프로토콜 사양
**Penguin Web Messaging - E2EE 서비스**

## 1. 소개
Penguin Web Messaging은 이중 서비스 아키텍처로 운영됩니다:
1. **일반 채팅 (Normal Chat):** 빠르고 동기화된 기능이 풍부한 메시징.
2. **E2EE 서비스:** **CXHKAS** 프로토콜 제품군을 사용하여 최대의 보안과 개인 정보 보호를 제공합니다.

**CXHKAS** (X 해시 비교, 비대칭 키, 대칭 키) 프로토콜은 실시간 화상 통화를 대역 외(OOB) 검증 채널로 활용하여 중간자(MitM) 공격을 제거하도록 설계되었습니다. 서버는 신뢰할 수 없는 것으로 간주되며(Trustless 아키텍처), 신원 확인은 전적으로 사용자에 의해 수행됩니다.

이 문서는 프로토콜의 두 가지 변형을 정의합니다:
- **C2HKAS:** 1대1 보안 채팅용 (2개의 해시).
- **C3HKAS:** 그룹 보안 채팅용 (3개의 해시).

## 2. C2HKAS (1대1 채팅)
**C2HKAS**는 **2**개의 **H**ash(해시), **A**symmetric(비대칭) **K**ey(키), **S**ymmetric(대칭) **K**ey(키)의 **C**omparison(비교)을 의미합니다.

### 2.1. 핸드셰이크 흐름
1. **비대칭 키 생성:** 사용자 1은 비대칭 키 쌍(공개/개인)을 생성합니다. 사용자 2는 영구적인 비대칭 키 쌍이 필요하지 않습니다.
2. **공개 키 교환:** 사용자 1이 서버를 통해 사용자 2에게 공개 키를 보냅니다.
3. **해시 비교 1 (루트):** 사용자 1과 사용자 2가 실시간 화상 통화를 시작합니다. 사용자 1의 공개 키에 대한 암호화 해시(예: 8자리 지문 `B J H 7 - G 5 A R`)를 비교합니다.
4. **대칭 키 생성:** 확인이 완료되면 사용자 2는 강력한 대칭 키(예: AES-256-GCM)를 생성합니다. 사용자 2는 확인된 사용자 1의 공개 키를 사용하여 이를 암호화하고 서버를 통해 전송합니다.
5. **복호화 및 해시 비교 2 (페이로드):** 사용자 1은 개인 키를 사용하여 대칭 키를 복호화합니다. 두 사용자 모두 실시간 화상 통화 중에 대칭 키의 해시를 비교합니다.
6. **세션 설정:** 두 해시가 일치하면 E2EE 세션이 설정됩니다. 모든 후속 메시지는 이 대칭 키를 사용하여 암호화됩니다.

## 3. C3HKAS (그룹 채팅)
**C3HKAS**는 **3**개의 **H**ash(해시), **A**symmetric(비대칭) **K**ey(키), **S**ymmetric(대칭) **K**ey(키)의 **C**omparison(비교)을 의미합니다.

대규모 그룹에서 관리자가 모든 구성원과 개별적으로 키를 확인하는 것은 비현실적입니다. C3HKAS는 **신뢰 체인(Chain of Trust)**을 사용하여 이 문제를 해결합니다.

### 3.1. 핸드셰이크 흐름
1. **관리자 루트 확인:** 관리자와 사용자 1이 C2HKAS를 수행합니다. 사용자 1은 관리자의 공개 키 해시를 확인합니다.
2. **체인 배포:** 사용자 1은 사용자 2의 공개 키를 확인하고 암호화된 대칭 키를 사용자 2에게 보냅니다. 사용자 2는 사용자 3을 확인하는 식으로 계속됩니다.
3. **오프라인 지원:** 사용자가 오프라인인 경우 해당 사용자의 체인이 일시 중지됩니다. 이전 사용자는 오프라인 사용자가 돌아올 때까지 키를 보관합니다.
4. **해시 비교 3 (그룹 페이로드):** 관리자가 최종 그룹 대칭 키 해시를 브로드캐스트합니다. 모든 온라인 사용자가 이 해시를 비교합니다.
5. **악의적인 행위자 격리:** 사용자의 해시가 관리자의 해시와 일치하지 않으면 체인을 역으로 감사합니다. 키가 변조된 노드가 악의적인 행위자로 식별됩니다.

## 4. 보안 고려 사항
- **신뢰할 수 없는 서버:** 서버는 릴레이 역할만 하며 대칭 키를 읽을 수 없습니다.
- **대역 외(OOB) 검증:** 실시간 화상 통화는 MitM 공격에 대한 궁극적인 진실의 원천입니다.
- **전방 비밀성 (Forward Secrecy):** (향후 범위) 보안 강화를 위해 Double Ratchet 알고리즘을 사용하여 키를 교체할 수 있습니다.

# <a id="chinese"></a>🇨🇳 CXHKAS 协议规范
**企鹅网络通讯 - E2EE 服务**

## 1. 简介
企鹅网络通讯采用双服务架构：
1. **普通聊天 (Normal Chat):** 高速、同步且功能丰富的消息传递。
2. **E2EE 服务:** 使用 **CXHKAS** 协议系列实现最高级别的安全性和隐私性。

**CXHKAS**（比较 X 个哈希、非对称密钥、对称密钥）协议旨在通过利用实时视频通话作为带外 (OOB) 验证通道来消除中间人 (MitM) 攻击。服务器被视为不受信任（无信任架构），身份验证完全由用户执行。

本文档定义了该协议的两种变体：
- **C2HKAS:** 用于 1 对 1 安全聊天（2 个哈希）。
- **C3HKAS:** 用于群组安全聊天（3 个哈希）。

## 2. C2HKAS (1 对 1 聊天)
**C2HKAS** 代表 **比**较 **2** 个 **哈**希、**非**对称密钥、**对**称密钥。

### 2.1. 握手流程
1. **生成非对称密钥:** 用户 1 生成非对称密钥对（公钥/私钥）。用户 2 不需要持久的非对称密钥对。
2. **交换公钥:** 用户 1 通过服务器将其公钥发送给用户 2。
3. **哈希比较 1（根）:** 用户 1 和用户 2 发起实时视频通话。他们比较用户 1 公钥的加密哈希（例如 8 个字符的指纹：`B J H 7 - G 5 A R`）。
4. **生成对称密钥:** 验证后，用户 2 生成强对称密钥（如 AES-256-GCM）。用户 2 使用用户 1 已验证的公钥对其进行加密，并通过服务器发送。
5. **解密和哈希比较 2（有效载荷）:** 用户 1 使用其私钥解密对称密钥。在实时视频通话期间，两个用户比较对称密钥的哈希。
6. **建立会话:** 如果两个哈希匹配，则建立 E2EE 会话。所有后续消息均使用此对称密钥加密。

## 3. C3HKAS (群组聊天)
**C3HKAS** 代表 **比**较 **3** 个 **哈**希、**非**对称密钥、**对**称密钥。

在大型群组中，管理员单独与每个成员验证密钥是不切实际的。C3HKAS 使用**信任链**解决此问题。

### 3.1. 握手流程
1. **管理员根验证:** 管理员和用户 1 执行 C2HKAS。用户 1 验证管理员的公钥哈希。
2. **链式分发:** 用户 1 验证用户 2 的公钥，并将加密的对称密钥发送给用户 2。用户 2 验证用户 3，依此类推。
3. **离线支持:** 如果用户离线，其信任链会暂停。前一个用户保留密钥，直到离线用户返回。
4. **哈希比较 3（群组有效载荷）:** 管理员广播最终群组对称密钥的哈希。所有在线用户比较此哈希。
5. **隔离恶意行为者:** 如果用户的哈希与管理员的哈希不匹配，则向后审核链。密钥被篡改的节点被识别为恶意行为者。

## 4. 安全注意事项
- **无信任服务器:** 服务器仅充当中继，无法读取对称密钥。
- **带外 (OOB) 验证:** 实时视频通话是抵御 MitM 攻击的最终事实来源。
- **前向保密 (Forward Secrecy):** （未来范围）可使用 Double Ratchet 算法轮换密钥以增强安全性。

# <a id="japanese"></a>🇯🇵 CXHKAS プロトコル仕様
**Penguin Web Messaging - E2EEサービス**

## 1. はじめに
Penguin Web Messagingはデュアルサービスアーキテクチャで動作します：
1. **通常チャット (Normal Chat):** 高速で同期された多機能なメッセージング。
2. **E2EEサービス:** **CXHKAS**プロトコルファミリーを使用した最大限のセキュリティとプライバシー。

**CXHKAS**（X個のハッシュ比較、非対称鍵、対称鍵）プロトコルは、ライブビデオ通話をアウトオブバンド（OOB）検証チャネルとして利用することで、中間者（MitM）攻撃を排除するように設計されています。サーバーは信頼できないもの（トラストレスアーキテクチャ）として扱われ、本人確認は完全にユーザーによって行われます。

このドキュメントでは、プロトコルの2つのバリエーションを定義しています：
- **C2HKAS:** 1対1のセキュアチャット用（2つのハッシュ）。
- **C3HKAS:** グループセキュアチャット用（3つのハッシュ）。

## 2. C2HKAS（1対1チャット）
**C2HKAS**は、**2**つの**H**ash（ハッシュ）の**C**omparison（比較）、**A**symmetric（非対称）**K**ey（鍵）、**S**ymmetric（対称）**K**ey（鍵）の略です。

### 2.1. ハンドシェイクフロー
1. **非対称鍵の生成:** ユーザー1は非対称鍵ペア（公開鍵/秘密鍵）を生成します。ユーザー2は永続的な非対称鍵ペアを必要としません。
2. **公開鍵の交換:** ユーザー1はサーバーを介してユーザー2に公開鍵を送信します。
3. **ハッシュ比較1（ルート）:** ユーザー1と2はライブビデオ通話を開始します。ユーザー1の公開鍵の暗号化ハッシュ（例：8文字の指紋 `B J H 7 - G 5 A R`）を比較します。
4. **対称鍵の生成:** 検証後、ユーザー2は強力な対称鍵（AES-256-GCMなど）を生成します。ユーザー2はそれをユーザー1の検証済み公開鍵で暗号化し、サーバー経由で送信します。
5. **復号化とハッシュ比較2（ペイロード）:** ユーザー1は秘密鍵を使用して対称鍵を復号化します。両方のユーザーは、ライブビデオ通話中に対称鍵のハッシュを比較します。
6. **セッションの確立:** 両方のハッシュが一致する場合、E2EEセッションが確立されます。後続のすべてのメッセージはこの対称鍵で暗号化されます。

## 3. C3HKAS（グループチャット）
**C3HKAS**は、**3**つの**H**ash（ハッシュ）の**C**omparison（比較）、**A**symmetric（非対称）**K**ey（鍵）、**S**ymmetric（対称）**K**ey（鍵）の略です。

大規模なグループでは、管理者がすべてのメンバーと個別に鍵を検証することは現実的ではありません。C3HKASは**信頼の連鎖 (Chain of Trust)**を使用してこの問題を解決します。

### 3.1. ハンドシェイクフロー
1. **管理者ルートの検証:** 管理者とユーザー1がC2HKASを実行します。ユーザー1は管理者の公開鍵ハッシュを検証します。
2. **チェーン配布:** ユーザー1がユーザー2の公開鍵を検証し、暗号化された対称鍵をユーザー2に送信します。ユーザー2がユーザー3を検証し、以下同様に続きます。
3. **オフラインサポート:** ユーザーがオフラインの場合、そのユーザーのチェーンは一時停止します。前のユーザーは、オフラインのユーザーが戻るまで鍵を保持します。
4. **ハッシュ比較3（グループペイロード）:** 管理者が最終的なグループ対称鍵のハッシュをブロードキャストします。オンラインのすべてのユーザーがこのハッシュを比較します。
5. **悪意のあるアクターの特定:** ユーザーのハッシュが管理者のハッシュと一致しない場合、チェーンは逆方向に監査されます。鍵が改ざんされたノードが悪意のあるアクターとして特定されます。

## 4. セキュリティに関する考慮事項
- **トラストレスサーバー:** サーバーはリレーとしてのみ機能し、対称鍵を読み取ることはできません。
- **アウトオブバンド（OOB）検証:** ライブビデオ通話は、MitM攻撃に対する究極の真実の情報源です。
- **前方秘匿性 (Forward Secrecy):** （将来の範囲）セキュリティを強化するために、Double Ratchetアルゴリズムを使用して鍵をローテーションできます。
